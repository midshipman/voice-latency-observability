# Architecture, clocks and measurement points

This is the single entry point for how the path works, where each point is measured, why, and what it does and does
not prove. Evidence tags: **[code]** read from source; **[replay]** recorded events replayed offline;
**[real call]** observed on a real Twilio call of the original prototype (raw records not included);
**[Twilio]** Twilio Voice Insights platform record (Twilio clock and definitions).

Figures below were recorded on a prototype that used Chinese speech recognition. They show how the instrument behaves
and what the numbers mean. They are not a benchmark of this English deployment. Prices and plan terms were noted on
2026-10-21 and must be re-checked.

## 1. Physical path

| Seg | Where | What happens | What we observe directly |
| --- | --- | --- | --- |
| S1 | mouth -> mic -> Chrome -> Twilio Voice SDK | WebRTC (opus) to Twilio | local mic volume (`inputVolume`), not speech content |
| S2 | Twilio edge -> ConversationRelay STT (Deepgram nova-3-general) | transcription, partial (`last=false`) and final (`last=true`) | no audio; only prompt and speaker events from Relay over WebSocket |
| S3 | Relay -> our WebSocket `/ws` (Pages Function, inbound) | receive the final, start a turn | arrival time `receivedAt`, taken at WS callback entry before JSON parsing |
| S4 | `/ws` -> Workers AI (`@cf/meta/llama-3.3-70b-instruct-fp8-fast`, streamed) | generate the answer | request sent, stream returned, first non-empty token, stream end |
| S5 | `/ws` (outbound, same socket) -> Relay | each token sent as a `text` message, `last:true` at the end | start and return time of each `ws.send` |
| S6 | Relay -> TTS (ElevenLabs, Twilio default voice) | synthesize and return audio | no audio; only Relay notifications (agentSpeaking, tokens played) |
| S7 | Twilio -> SDK -> Chrome -> speaker | playback | local downlink volume (`outputVolume`), not physical sound |

The two `/ws` nodes are one Pages Function and one bidirectional socket, not two services.

Observation path (separate from the audio path): `/ws` records events (`rec`, batched into the `MetricsStore` Durable
Object) and publishes them live (`pub`, to `/live`). The browser draws the lamps from `/live` and sends its own
per-turn telemetry beacon. After the call, Twilio Voice Insights gives a platform-side record. The lamps show the
observation path, not the audio.

## 2. Clocks and IDs

- Three clocks: server (Cloudflare isolate `Date.now()` and `performance.now()`), browser, Twilio. Same-clock
  differences are precise; cross-clock differences are approximations.
- The page estimates a browser/server offset `clkOffset` from `/live` ping and pong assuming symmetric RTT/2. Equal
  one-way delay is not proven.
- IDs: `callSid` (Twilio), `sessionId` (Relay `VX...`), `utteranceId` = `<callSid>:u<N>` and `responseId` are
  generated by us (Relay does not pass them through), `relaySeq` is our arrival order of Relay messages.
- Observed consistency [Twilio][real call]: for inbound events, our `receivedAt` minus the Twilio record was between
  -15 and +5 ms (final, clientSpeaking, agentSpeaking on and off, interrupt). It is an observed range only. It
  includes network transit and Twilio's accounting semantics, and proves neither clock offset nor one-way delay.

## 3. Measurement points

| Point | Where [code] | Why here | Proves | Does not prove |
| --- | --- | --- | --- | --- |
| B1/B2 local speech start/end | call page, `inputVolume` >= 0.06 starts, quiet > 500 ms ends | only browser-side signal that the user is making sound | local mic activity (approximate) | not STT time, not sentence completion, not Relay's speech detection |
| R-in speaking, final, partial, interrupt | `/ws` dispatch in `_lib.js`, `receivedAt` at callback entry | raw Relay notifications, closest server observation to Twilio | arrival time, type, order | no transcript text is stored; partials are counted and folded into `partial_summary` |
| W1 `relay_final_received` | same, `last=true` prompt | start of a turn; only a final starts the LLM | final arrival at `/ws` | not the moment the user finished speaking |
| W2 `llm_request_start` | right before `env.AI.run()` | same-clock W3-W2 includes the call path in TTFT | request time | not model-internal time |
| `llm_response_stream_received` | when `env.AI.run()` returns the stream | separates "stream returned" from "first token" | stream return time | |
| W3 `llm_first_nonempty_token` | first non-empty token while reading | end of TTFT | first token arrival | not the end of the LLM stage |
| W4 `relay_text_send_start/returned`, seq 1 | around first `ws.send` | when we hand the first chunk to Relay | our send time; a 0 ms send only means the local write returned | not Relay's accounted `first_token_received` |
| W5 `llm_stream_end` | stream fully read | true end of generation | stream end time | separate event from W6 |
| W6 text send, `last=true` | the `last:true` `ws.send` | tells Relay the turn text is complete | our send time | whether Relay accepts it (interrupted turns get no `final_token_received`) |
| intermediate text chunks | counted in `turn.textChunks`; first, last, fallback and failed or skipped chunks kept in full | per-token logging is large and changes no lamp | count, characters, failures, max send time | middle chunk timing and content are not available afterwards |
| speaker, tokens_played | Relay call-level notifications | Relay's report of who speaks | when Relay says speech started or stopped | not tied to a turn; tokens_played is not "a turn finished playing" |
| `interrupt` | same | Relay decided there was an interruption | time, `durationUntilInterruptMs` | `utteranceUntilInterrupt` was empty in every observed case, so how far speech got is unknown |
| B3/B4 local downlink volume | `outputVolume` >= 0.05 starts, quiet > 800 ms ends | browser-side "there is downlink sound" | local WebRTC downlink volume (approximate) | not physical speaker output, not TTS latency |
| `/live` sequence `pseq` and reconciliation | `pub` carries a sequence, the page dedupes and reconciles | tells whether the page lost events | published, received, duplicate, missing counts | not audio loss |
| end record | `end`: `subrequests`, `subrequestsByPurpose` (gateAttach, gateBind, gateRelease, metricsBatch, livePubs), `recordedEventsByType`, `publishedByType`, `aggregated` | checks known call counts, records, degradation and drops | per-call internal call totals and known drops | per-message subrequest budget is unverified |

### The seven lamps [code]

Microphone = B1/B2. STT = inferred, from local speech start to the final returning (a merged wait, not STT latency).
WS in = W1 to W2. LLM = lit from W2 until W5 (`llm_stream_end`); the first token only shows "first token arrived, stream
continuing". WS out = waits from W3, passes when W4 seq 1 is sent (kept visible 700 ms, labeled as display hold, not
duration). TTS = inferred, from text sent to Relay agentSpeaking or local playback. Speaker = B3/B4 (local
approximation). Green = working, gray = idle. LLM and TTS may be lit together because streaming makes them truly
concurrent.

## 5. Cross-checking against Twilio Voice Insights

Reproduce with `node scripts/crosscheck-call.mjs <server-events.json> <insights.json>` (inputs are your own call data;
none is included). ConversationRelay events are under `Edge=carrier_edge` and are paginated; without an Edge only SDK
events return. `scripts/insights-calibrate.mjs` follows `next_page_url`.

### Counts (same call)
| Category | Ours | Twilio |
| --- | --- | --- |
| final / end_of_customer_speech | 9 | 10 (one extra speech fragment before the first sentence, with an stt_latency of 150 ms but no final) |
| client speaking on / start_of_customer_speech | 10 | 10 |
| agent speaking on / start_of_agent_speech | 8 | 8 |
| agent off / end_of_agent_speech | 7 | 7 |
| interrupt | 4 | 4 |
| first text chunk / first_token_received | 9 | 7 |
| last=true / final_token_received | 9 | 5 |

### What this showed
- `final_token_received` appears only on turns 1, 3, 5, 7, 9. The missing ones are exactly the four interrupted turns.
  That fits Relay not accounting `last=true` for an interrupted turn, but it does not prove whether sound played.
- Twilio's `first_token_received` is later than our W4 by 138, 615, 530, 989, 575, 693 and 1564 ms, while our
  `last=true` to Twilio `final_token` is only 10 to 26 ms. So W4 and Twilio's first_token are different events and must
  not be paired to calibrate a clock offset.
- Twilio's `start_of_agent_speech` minus `first_token_received` equals its `tts_latency` (139 to 337 ms). Twilio's
  "TTS latency" is therefore Relay's first accounted token to Relay reporting agent speech, and excludes the gap
  between our send and Relay's accounting.
- Twilio Summary `application_latency_ms` and `time_to_first_audio_ms` can be recomputed exactly from events
  (first_token_received minus final, and start_of_agent_speech minus final). The Summary's turn count (6) matches neither
  the 7 turns with a first token nor the 9 finals, so it is not used as a turn count. The summary was `partial` when read.
- Our TTFT (W3-W2) was 0.1 to 1.0 s, but time to Relay reporting agent speech (Twilio definition) was 0.76 to 2.02 s.
  That is not when the user hears sound.
- **Hypothesis, unverified:** Relay accumulates text (by sentence or length) before accounting and synthesizing. Testing it
  needs the chunk index and time of the first sentence-ending punctuation, which is not recorded today.
- Browser vs Twilio: local speech start was 149 to 2133 ms earlier than Twilio `start_of_customer_speech` (nearest
  neighbor pairing, ambiguous); local playback start was 273 to 420 ms later than Twilio `start_of_agent_speech` on five
  turns (offset estimate 133 ms, RTT 186 ms, symmetric assumption, no proven error bound). One turn showed a 9930 ms
  gap with two play episodes and the cause is not determined.

## 6. Are the points suitable?

Criteria: (1) placed on the same code path next to the measured action, (2) same-clock differences, (3) the same event
exists in an independent record with matching counts, (4) inference is never presented as observation.

- R-in: suitable. Counts match Twilio and pairs differ by -15 to +5 ms. Twilio had one extra end_of_customer_speech.
- W1: suitable as "we received the final", not as "user finished".
- W2, stream_received, W3, W5: suitable (same clock, adjacent code). No Twilio counterpart, so only self-consistent.
- W4/W6: suitable as "we sent", not as "Relay received or began synthesis".
- B1 to B4: approximations only; they differ from Relay detection by hundreds of ms to 2 s.
- Intermediate chunk counts: meet the "head, tail and exceptions" rule at the cost of not being able to inspect Relay buffering.

## 7. What cannot be proven

- Physical speaker output or what a person heard. Local SDK downlink volume is not physical sound.
- True STT or TTS latency. Twilio's `stt_latency` and `tts_latency` use Twilio definitions; only tts_latency =
  first_token to agent speech was confirmed.
- One-way network delay. RTT/2 is an approximation.
- Why final transcripts sometimes arrive early (no transcript or audio is stored). Effective settings seen in Insights
  were `speechTimeout="0"` and `turnDetection="OFF"`. Our TwiML sets neither. Twilio documents `speechTimeout` values
  600 to 5000 and default `auto`; `turnDetection` is not in the public docs, so whether `0`/`OFF` equals `auto` is unverified.
- Per-message subrequest budget and all behavior over long mobile calls.
- A scripted synthetic-audio call is not a substitute for a human call on a phone.
